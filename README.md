# FaceMatch

2枚の顔から「好きなほう」を選ぶ操作を繰り返して、**自分がどんな顔をタイプだと感じているか**を診断する Web アプリです。
名前は Facebook の前身である FaceMash に由来します。

輪郭・目の大きさ・タレ目/ツリ目・眉・鼻・口・髪など **14項目**について、
「どの特徴をどれだけ重視して選んでいたか」と「その特徴のどのあたりが好みか」を推定します。

- **インストール不要** — ブラウザで開くだけ。顔画像291枚を同梱しているのですぐ遊べます
- **端末内で完結** — 推定も結果の保存もすべてブラウザの中。どこにも送信されません
- ビルド不要（素の HTML + ES モジュール）、実行時の外部通信なし
- スマートフォン対応・ダークモード対応
- ホーム画面に追加するとアプリのように単独で起動します（PWA）

## 目的

このアプリには2つの目的があります。

1. **自分の顔の好みを知る**
2. **かわいい人を見て楽しむ**

判断に迷ったらこの2つに立ち返ります。
とくに 2 があるため、同梱する顔は「診断の精度が上がるかどうか」だけでは決めません。
狙い（アイドル・女優くらいのかわいさ）から明らかに外れた顔は、
精度に多少のマイナスがあっても入れません。見ていて楽しくないこと自体が損失だからです。

## いまの課題と次の一手

**顔のパーツごとに「結果の出やすさ」が偏っています。**原因は項目どうしの相関で、
実測で裏づけが取れています（[項目ごとの偏りを直す](#項目ごとの偏りを直す)）。

**相関は層ごとに見てください。** `choosePair` は同じ層の顔しか並べないので
（[仕組み 5](#5-かわいさの層をまたいで並べない)）、診断で効いているのは
プール全体の相関ではなく**層の中の相関**です。出題の大半は `cute` 層から出ます。

| | いま（291枚） | 目標 |
|---|---|---|
| `cute` 層247枚の最大相関 | **0.80**（小鼻の広さ ↔ 口の大きさ／目尻の角度 ↔ 眉の角度） | **0.6以下** |
| プール全体291枚の最大相関 | 0.83（同じ組） | – |
| 結果の出やすさの幅 | **1.40倍**（291枚・較正後の実測。x1.23〜x0.88） | 1.0倍に近づける |

顔を足して相関を切る方法自体は効いています。当初いちばん重かった
`眉と目の距離 ⇔ 眉の形` は **0.86 → 0.63** まで下がりました。
いま残っているのは `小鼻の広さ ⇔ 口の大きさ`（0.81）と
`目尻の角度 ⇔ 眉の角度`（0.80）で、**後者は眉なのでプロンプトでは動きません**
（[1組に集中させても眉は動かなかった](#1組に集中させても眉は動かなかった)）。
つまり鼻と口を直しても、最大相関は 0.80 で止まります。

相関だけを変えて測ると、重要項目の当てやすさは相関 0.9 で 67.0%、0.6 で 78.7%、
0.2 で 82.7% でした。**0 を目指す必要はなく、0.6 を切れば十分**です。
そこから先を追うと、現実にはいない組み合わせの顔が増えて目的2を損ないます。

手持ちの顔を選び直しても届きません（71枚から52枚を選んでも 0.83 → 0.71 止まり）。
**相関を切る顔を新しく作るのが唯一の手**です。

```bash
npm run generate -- --decorrelate --count 60 --budget-jpy 500 --out .cache/decor
npm run analyze -- --from .cache/decor --out .cache/decor/faces --json .cache/decor/faces.json --gender female
npm run gap-check -- .cache/decor/faces.json
```

### 顔を足すときの決まり

このリポジトリは「測ってから変える」で進めてきました。顔を足すときも同じです。

1. **かわいさの基準は人が決める** — 生成した顔は必ず本人に見せて、採否をもらう。
   アイドル・女優くらいのかわいさが基準（[目的](#目的)の2つめ）。18〜25歳
2. **足す前に測る** — `gap-check` で枠を埋めるか、`npm test` で精度が下がらないかを見る。
   **精度が下がるなら足さない**
3. **相関を強める顔は足さない** — 枠を埋めない顔は、足しても偏りは直らない
4. **APIキーはチャットに貼らせない** — 環境変数か、クラウド環境の API credentials で渡す
   （[API で顔をまとめて生成する場合](#api-で顔をまとめて生成する場合)）

## 仕組み

### 1. 顔画像に特徴量を紐づける

「どんな顔が好きか」を言葉で言い当てるには、画像そのものではなく**画像の特徴が数値化されている**必要があります。
そこで取り込み時に [face-api](https://github.com/vladmandic/face-api) で顔検出・68点ランドマーク・年齢/性別推定を行い、
両目間の距離で正規化した幾何量（顔の縦横比、目の開き、目尻の傾き、眉と目の距離、小鼻の幅、唇の厚みなど）と、
画素統計（肌の明るさ、髪の明るさ、髪の長さ）を実測して `data/faces.json` に保存します。
実測するのは15項目ですが、**髪の長さは診断には使いません**
（[髪の長さは測っても診断には使わない](#4-髪の長さは測っても診断には使わない)）。診断に使うのは14項目です。

絶対値のままでは「大きい/小さい」の基準が決まらないため、アプリ側で**プール内の順位**に変換し、
すべての特徴を 0.0〜1.0 の相対値にそろえます（`src/features.js`）。

### 2. 選択から好みを推定する

特徴 k について理想値 `m_k` と重視度 `s_k` があると考え、顔 x の好ましさを

```
u(x) = -Σ_k s_k (x_k - m_k)²
```

とする**理想点モデル**を使います。2択の勝率は `P(A) = sigmoid(u(A) - u(B))` で、
これを比較データから MAP 推定します（`src/model.js`）。

単純な重み付き和ではなく理想点モデルを使うのは、

- 「大きすぎても小さすぎても嫌、中くらいが好き」という好みを表現できる
- 重視していない特徴は `s_k` がほぼ 0 に落ちるので、**こだわりの有無を分離できる**

ためです。

### 3. 出す2枚を選ぶ

ランダムに2枚出すと14項目すべてが同時に違ってしまい、どの特徴が効いたのか分離できません。
そこで毎回、候補ペアの中から

- まだ観測の薄い特徴で差がついている
- すでに分かった特徴では差が小さい
- 現在のモデルの予測が五分五分（＝情報量が大きい）
- 同じ顔が出すぎていない

ものを選びます。

シミュレーション（`npm test`）では、この選び方でランダム出題より明確に精度が上がりました
（プールが小さかった頃の実測です）。

| 出題方法 | 20回 | 30回 | 45回 |
|---|---|---|---|
| ランダム | 73.6% | 78.5% | 83.6% |
| 適応的（本アプリ） | **77.7%** | **83.0%** | **86.0%** |

同梱プールで測ると次の通りです（`npm run acc-check`）。
画面に出している精度はこの値です。**305枚のときの実測で、291枚では未確認です。**

| 問数 | 20 | 30 | 45 | 90 |
|---|---|---|---|---|
| 予測一致率 | 79% | 82% | 85% | **89%** |

45問で頭打ちに見えたのは顔の枚数ではなく問数が原因でした。
14項目を45回の二択で推定するには情報が足りず、同じプールでも
90問なら89%まで伸びます。そのため「とことん（90問）」を用意しています。

数値は、好みを持つ仮想ユーザーに選ばせ、その回答だけから推定したモデルが
**未知のペアで仮想ユーザーの好みを当てられた割合**です（60試行の平均）。

### 4. 髪の長さは測っても診断には使わない

実測は15項目ですが、**診断に使うのは14項目**です。髪の長さだけは
「好みを測る対象」ではなく「ペアを選ぶときにそろえるもの」にしています。

ロングとベリーショートを並べると「顔がどうであれ短いほうは選ばない」人が出て、
その回は顔の好みではなく髪の好みしか測れません。実測では、髪を顔より重視する人の
**顔の項目の的中率が 45.2%** しかなく、**結果の 98.7% が「髪を見ていました」**に
なっていました。

かといってペアの選び方だけで髪をそろえると、今度は髪の長さ自体が測れなくなります。
測定項目に残したままだと「測れない項目を1つ抱える」ぶん精度が落ちるので
（予測一致率 0.849 → 0.816）、測定項目から外しました。

正規化した値自体は残してあり（`hairOf`）、`choosePair` が髪の長さの近い2枚を
選ぶのに使います。結果画面の「髪と肌」は**髪の明るさと肌の明るさの2項目**です。

### 5. かわいさの層をまたいで並べない

同梱プールの顔には `tier`（かわいさの層）が付いています。

| 層 | 枚数 | 役割 |
|---|---|---|
| `cute` | 247 | 主役。アイドル・女優くらいのかわいさ |
| `plain` | 24 | かわいさを指定せずに作った、顔のパーツの幅を広げるための層 |
| `edge` | 20 | 項目の端を狙い撃ちして作った層。端を作るにはかわいさの指定を弱めるしかない |

`plain` と `edge` はどちらも、かわいさの水準が `cute` から外れます。

**`choosePair` は違う層どうしを並べません。**
かわいい顔とそうでない顔を並べると誰でもかわいい方を選ぶので、その回は
「その人の好み」ではなく「世間一般のかわいさ」しか測れないためです。
しかも顔のパーツとかわいさには相関があり（削除済みの顔を測ると
あごのライン AUC 0.83 / 眉と目の距離 0.18 / 輪郭の縦横比 0.22）、
混ぜたまま出すと**全員が同じ結果に寄っていきます**。

判定は層の名前を見ず「違う層どうしかどうか」だけを見るので（`tierOf`）、
層を増やしてもコードの変更は要りません。

実測でも、層を分けずに混ぜると精度は下がりました（45問・仮想ユーザー120人）。

| | 予測一致率 | 重要項目Top3的中 |
|---|---|---|
| かわいい層だけ 43枚 | 85.5% | 59.2% |
| ＋27枚・層を分けずに混ぜる | 78.5% | 48.1% |
| ＋27枚・同じ層どうしだけ | 86.1% | 65.3% |

何枚足すのが程よいかも測りました（45問・仮想ユーザー300人・同じ層どうし）。
12枚あたりでだいたい頭打ちになり、それ以上足しても伸びないまま
`plain` 層の出題割合だけが増えます。

| 足す枚数 | 予測一致率 | Top3的中 | Top5内 | 出題のうち `plain` 層 |
|---|---|---|---|---|
| +0（計43） | 86.3% | 62.9% | 77.2% | 0% |
| +6（計49） | 86.2% | 60.8% | 76.3% | 10% |
| **+12（計55）** | **86.3%** | **64.7%** | **80.0%** | **19%** |
| +18（計61） | 86.9% | 68.6% | 80.7% | 28% |
| +27（計70） | 86.5% | 64.0% | 80.3% | 38% |

この測定をした当時、`plain` は9枚でした。いまは `plain` 24枚 + `edge` 20枚で、
プール291枚の15%を占めます。**45問あたりの出題割合は測り直していません。**

**`plain` 層の回はスキップできません。**
見たい顔ではないので飛ばされやすい一方、顔のパーツの幅がいちばん広いのがこの層です。
飛ばされるとこの層を入れた意味がなくなります。

| | 予測一致率 | Top3的中 | 飛んだ回 |
|---|---|---|---|
| 全部答える（NO SKIP） | 86.1% | 63.7% | 0% |
| スキップできると8割飛ばす | 82.4% | 53.6% | 33% |

飛ばせるままだと、層を足す前（62.9%）より悪くなります。

なお `npm test` の数値（上の表）は `plain` 層を足しても横ばいです（45問で 87.0% → 86.8%）。
あの仮想ユーザーは**かわいさで選ばない**ので、層を分けること自体が
使える比較を減らすだけになるためです。`--attr 3` を付けると
「かわいい方をほぼ必ず選ぶ」ユーザーになりますが、層をまたぐペアを
そもそも出さないので適応出題の結果は変わりません。**これが狙いどおりの状態です。**
かわいさで選ぶ人に対して効いているかは、上の3つの表で測っています。

### 結果から「理想の顔」を作る

診断はプールから選ぶだけなので、その人の理想そのものがプールに入っているとは限りません。
そこで結果画面から、測った理想値をプロンプトに直して**その場で1枚生成**できます
（`src/ideal.js`）。

使うのは**重視度の上位6項目だけ**です。全部入れると指示が多すぎて生成器が取りこぼします。
撮り方とかわいさの指定はプールにそろえ、髪の長さは測っていないのでロングに固定します。
失敗したら黙って作り直します（最大4回、待ちを1.2秒ずつ延ばす）。混雑や画像が返らない
場合は作り直せば通ることが多く、鍵違いと API 上限は待っても無駄なのですぐ止めます。

**API キーはリポジトリのどこにも置いていません。** 静的サイトなので同梱すると
ソースを見た誰もが読み取れて、持ち主の残高を使えてしまいます。ブラウザ側で
パスワードを確認しても、鍵が手元にある前提の見せかけにしかなりません。
そのため**入力欄に鍵そのものを入れてもらう方式**にしています。鍵を知っている人だけが
使えて、鍵は端末の外に出ません（`sessionStorage` にのみ残ります）。

他の人にも使わせるならサーバーが要ります。

### 結果の見出し

一番上は**一言**で言い、その下に内訳を掛け算の形で出します。

```
あなたのタイプ
丸顔のかわいい系タイプ
丸顔 × ぱっちり目 × 厚め唇
```

一言のほうは「いちばん見ていたパーツ＋きれい系／かわいい系」だけにしています。
系統は言い切れる根拠があるときだけ付き、無ければ「丸顔タイプ」になります。
どのパーツも目立って見ていなければ「雰囲気で選ぶタイプ」です。

### 結果はスライドで1枚ずつ見せる

数字をいきなり全部出すより、1つずつ開けていくほうが見ていて楽しいので、
結果はまずスライドで見せます。タップで次へ進み、最後にまとめへ渡します。

```
1. 結果が出ました          ← 何回の選択を読んだか
2. いちばん見ていたのは◯◯   ← 部位の棒が伸びる
3. ◯◯が◯%を占めていました  ← どちら寄りかのつまみが動く
4. あなたは◯◯系           ← きれい系⇔かわいい系
5. 診断が当たる確からしさ◯% ← 数字が0から数え上がる
6. いちばん近い顔は         ← いちばんの見どころ。最後に取っておく
7. ◯◯タイプ              ← タップでまとめへ
```

右上の「スキップ」でいつでもまとめへ飛べます。「前回の結果」から開いたときは
一度見たものなので、スライドを出さずにまとめを直接出します。

`prefers-reduced-motion` が指定されている環境では動きを止めます。

### 結果画面の割合は2つの群でそろえる

割合の分母は**顔の項目だけ**と**髪と肌だけ**の2つで、群の中で 100% になります。
群どうしの大きさは「選ぶときの 10% は髪と肌で決まっていました」の一文が受け持ちます。

以前は分母が3通りありました。見出し下のタグが14項目すべて、内訳が顔の12項目、
部位のまとめがまた別で、**同じ項目が 37% と 46% の2通りで出ていました**。
分母をそろえたので、部位の割合はその内訳の合計になります（目 74% =
目の間隔 42% + 目の大きさ 27% + 目尻の角度 5%）。

顔と髪・肌を同じ分母で並べてはいけません。顔の 35% と髪の 7% が比べられるように
見えますが、髪と肌はもともと2項目しかないので、少なく見えるだけです。

### 読めない差は出さない

内訳に出すのは**10%以上の項目を上位3つまで**で、残りは「くわしく見る」に入れます。
5% と 4% の差は読み取れません（項目ごとの確からしさは 6〜8割です）。
以前は最低6項目を必ず出していたため、いちばん大きいカードの半分が
意味のない行で埋まっていました。

### 順番は、楽しさが先

「好みに近い顔」を1位だけ大きくして先頭に置き、「選んだ顔」を続けます。
数値のカードはその後ろです。診断の結果として最初に見たいのは顔で、
分析ではないためです。

## 使い方

### 遊ぶ

公開されたURLを開き、問数を選んで**もう一度押すと始まります**（「はじめる」ボタンはありません）。
あとは2枚から好きなほうを選ぶのを繰り返すだけです。

問数は 20 / 30 / 45 / 90 と **おまかせ** から選べます。おまかせは回数を決めず、
重視している上位3項目の顔ぶれが3回続けて変わらず、推定精度が 82% に届いた時点で
終わります（最短12問・最長60問。`src/model.js` の `AUTO_STOP`）。

スタート画面に出している精度は、同梱プールでの実測値です。
**顔を足したり較正を変えたら測り直してください**（`src/app.js` の `ROUNDS` の `acc`）。
1回に数分かかるので、走らせるのは必要なときだけにしてください。

```bash
npm run acc-check
```

| 回数 | 20 | 30 | 45 | 90 |
|---|---|---|---|---|
| 精度（305枚・較正後） | 79% | 82% | 85% | 89% |

**291枚では未確認です。**同一人物を外し、顔を足してプールが変わったので、測り直しが必要です。

**18〜25歳の女性の顔291枚を同梱しているので、開いてすぐ診断できます。**

結果はブラウザの localStorage にのみ保存され、どこにも送信されません。

### 顔を追加する

顔の追加はコマンドで行い、結果をリポジトリに同梱します。アプリ側に管理画面はありません。

```bash
npm install
npm run analyze -- --from <画像フォルダ> --gender female --append
```

`data/faces/*.jpg`（顔を中心にそろえた正方形）と `data/faces.json`（特徴量）が更新されます。
顔が検出できない画像、顔が端に寄りすぎている画像は自動的に除外されます。

診断には**片方の性別で12枚以上**必要です。枚数が多いほど精度は上がります。
男性の顔を追加すれば、スタート画面に性別の選択肢が増えます。

| オプション | 既定値 | 説明 |
|---|---|---|
| `--from` | （必須） | 入力画像フォルダ |
| `--gender` | – | `female` / `male`。自動判定を使わず全件その性別として扱う |
| `--append` | – | 既存の `faces.json` に追加する |
| `--multi` | – | 1枚の画像に写っている顔を全員取り込む |
| `--tier` | `cute` | かわいさの層。`plain` / `edge` を指定すると幅を広げるための層として取り込む |
| `--size` | 480 | 書き出す画像の一辺 |
| `--limit` | 制限なし | 先頭 N 枚だけ処理する |
| `--debug` | – | 検出したランドマークと肌/髪の採取位置を重ねた確認用画像を出力する |

性別は自動で判定できますが、**ショートヘアの女性を男性と誤ることがある**ため、
性別が分かっている画像をまとめて取り込むときは `--gender` を指定してください。

計測が意図どおりか疑わしいときは `--debug .cache/debug` を付けて、
書き出された画像でランドマークと採取位置（水色=頬、黄=髪色、緑枠=髪の走査域、緑線=検出した髪の下端）を
目で確認してください。実行後には項目ごとの実測値のばらつきも表示されます。

### 顔画像を用意する

**実在の人物ではなく、AI が生成した架空の顔を使うことを推奨します。**
実在する人の顔を「好み」で採点させることを避けるためと、
知っている顔が混ざると「顔の造作」ではなく「その人への好意」で選んでしまい、結果がずれるためです。

生成用のプロンプトを書き出せます。

```bash
npm run generate -- --dry-run --count 24 --female-ratio 1 --out .cache/raw
```

| ファイル | 用途 |
|---|---|
| `prompts.txt` | 1件ずつ完結したプロンプト |
| `prompts-chat.txt` | 共通条件を最初に1回送り、以降は1行ずつ送る形式。**スマホ向け** |

`--female-ratio 1` で女性のみ、`0` で男性のみになります。
診断の精度は**プールが特徴空間をどれだけ広くカバーするか**で決まるため、
輪郭・目・眉・鼻・唇・髪・肌・年齢の属性グリッドから均等に組み合わせを引いてプロンプトを作ります。

生成時は次の2点が計測の前提です。

- **正面向き** — 顔が大きく傾いたり横を向いていると、ランドマークの精度が落ちます。
- **無地の背景** — 「髪の長さ」は髪色に近い画素があごの下へどこまで伸びているかで測るため、
  背景が雑多だと髪と背景を分離できません。四隅の色がばらついている画像では、
  この項目を**計測不能として除外**します（他の項目は影響を受けません）。

スクリーンショットではなく画像そのものを保存してください。画面の余白やUIが写り込むと背景が無地でなくなります。

対応形式は jpg / png / webp / heic / heif / tiff / gif です。ただし
iPhone のカメラ形式である HEIC(HEVC) は sharp の標準ビルドでは読めないため、
その場合は JPEG に変換してから渡してください。

### 顔の大きさをそろえる

切り出し枠の広さは両目の間隔 d を単位に決めます（`chooseBox`）。
枠が広いほど顔は小さく写るので、**1枚だけ顔が小さいと、その顔は中身ではなく
「小さいから」選ばれにくくなり、集めた選択がゆがみます**。

枠の取り方を決めたときの実測（当時115枚）では、枠は d の 4.70〜5.13倍 にそろっていました。
外れていた2枚は、どちらも頭頂の実測が髪のほつれや背景のムラを上に拾い、
その分だけ枠が広がっていました（6.36倍 と 5.35倍）。

- 上限を **d の 5.2倍** にして、広がりすぎを止める
- **縦の位置は、頭頂ではなく「あご」を基準に置く**（下記）
- **枠が元画像からはみ出すときは、埋める前にまず枠を縮めて画像の中へ寄せる**

縦の位置を頭頂から測ると、頭頂の実測が外れた分だけ顔がずれます。切り詰めた分を
上下に振り分けても、**誤差の半分は残ります**（実際に1枚だけあごが 91.1% まで
下がり、顔が枠の下に寄りました。他は 79.1〜81.5%）。
あごはランドマークで確実に取れるので、そこを基準に **枠の上から 80.3%** の位置へ
置きます。この値は同梱プールの実測の中央値で、従来の枠の取り方
（あごの下に 0.95d 残す）とも一致するため、正常な顔の見た目は変わりません。

最後の1点は、はみ出しを背景色で埋めると**完全に無地の帯**ができ、
そこだけ作った画素だと分かってしまうためです。下限（d の 4.0倍）を
割るときだけ、最後の手段として埋めます。

顔の大きさがそろっているかは、切り出し済みの画像を検出し直して確かめられます。
この確認をしたときは全114枚が中央値の 0.93〜1.07倍、あごの位置が 79〜81% に収まっていました（291枚では未確認）。

### 同じ人物が重複していないか確かめる

同一人物が複数入っていると、その人の特徴に結果が引っ張られます。

```bash
npm run find-duplicates -- <画像フォルダ> --json data/faces.json
```

画像生成器は放っておくと**同じ顔を髪型だけ変えて使い回す**ため、
見た目だけで判定すると別人まで巻き込みます。`--json` に解析結果を渡すと、
見た目と実測値の両方で近い組だけを重複として挙げます。

実写の別人同士は距離 0.5〜0.75 ですが、同じ生成器で作った顔は別人でも
これを大きく下回ります。同梱291枚の中央値は 0.34 で、実写の別人よりも近いです。

#### しきい値は絶対値で決めてください

`find-duplicates` が「重複の候補」として出すのは**プール自身の下位2%**です。
これは相対基準なので、**どれだけきれいにしても必ず約2%を挙げ続けます。**
実際に52枚・74枚と外したあとの305枚でも、また124枚が候補に挙がりました。
出力は「近い順に並べたもの」として読み、外す線は自分で決めてください。

このリポジトリでは **見た目の距離 0.20** を境界にしています。

**連結成分でまとめてはいけません。** a≈b, b≈c なら a と c も同じ組になるため、
305枚のときは23枚が1グループになりました。この23枚の相互距離は最大 **0.369** で、
プール中央値 0.344 より遠く、別人同士です。まとめて外すと22枚を無駄に失います。

正しくは「**残った顔どうしが必ずしきい値より離れている**」状態を作ります。
近い組から順に、他の顔との平均距離が小さいほう（個性の薄いほう）を外していきます。
305枚に対して 0.20 で適用すると34枚が対象になり、33組すべて目で確認したところ、
どれも顔が同じで髪色・髪型だけが違うものでした。

| しきい値 | 近い組 | 外す枚数 |
|---|---|---|
| 0.19 | 15組 | 13枚 |
| **0.20** | **47組** | **34枚** |
| 0.21 | 124組 | 59枚 |

### 精度の弱点を調べて、それを補う画像を作る

診断の精度が上がらない原因は主に2つです。

1. **その項目の端にあたる顔が少ない** — 片側しかないと好みの位置を決められない
2. **2つの項目が相関している** — 例えば小鼻が広い顔がいつも口も大きいと、
   どちらを重視しているのか切り分けられない

```bash
npm run coverage -- data/faces.json
```

項目ごとに「測定ノイズに対して何段階見分けられるか」と分布の片寄り、
さらに項目どうしの相関を表示します。

弱点が分かったら、それを補う画像のプロンプトを作れます。

```bash
npm run generate -- --dry-run --fill data/faces.json --count 24 --out .cache/fill
```

足りない端を埋める指定と、相関を崩すための逆の組み合わせ
（例: 小鼻は細いが口は大きい）を含んだプロンプトが出ます。
各プロンプトには何を補うためのものかが添えられます。

### かわいさ優先で作って、あとから選ぶ

文章で骨格を動かそうとすると顔が崩れます。パーツを個別に指定しても実測値は動かず、
強く書けばブサイクになり、顔の「型」で指定しても同じでした。
生成器が得意なのは「かわいい顔を作ること」だけです。

そこで狙って散らすのはやめ、**かわいさだけを指定してたくさん作り、
その中から実測値が離れているものを選びます**。

```bash
# 1. かわいさだけを指定したプロンプトを作る（顔のパーツには触れない）
npm run generate -- --dry-run --plain --count 24 --female-ratio 1 --out .cache/plain

# 2. できた画像を候補として解析する（data/ にはまだ入れない）
npm run analyze -- --from .cache/plain --out .cache/cand/faces --json .cache/cand/faces.json --gender female

# 3. プールの幅をいちばん広げる顔を選ぶ
npm run pick -- .cache/cand/faces.json --count 6
```

`pick` は「見分けられる段階数」の合計が増える顔を順に選び、
どの項目を広げたのかも表示します。足しても幅が広がらない顔は選ばれません。

### かわいさを保ったままばらつきを増やす

パーツを個別に指定しても実測値は動きません。「細い目」と書いても、
生成器が持つ「かわいい顔の正解値」から離れないためです。
顔の**型**ごと指定すると骨格が入れ替わるので、かわいさを保ったまま散らせます。

```bash
npm run generate -- --dry-run --spread --count 20 --female-ratio 1 --out .cache/spread
```

たぬき顔・犬顔・猫顔・うさぎ顔・童顔・韓国アイドル風・ハーフ顔・
儚げ系・大人かわいい・ぱっちり丸顔の10種類を順に作ります。

並べるのは「かわいい」の範囲にある型だけです。
狐顔・クール系・彫り深めも骨格は散りますが、きれい系であってかわいくはないため、
目的2（かわいい人を見て楽しむ）から外れるので入れていません。

### 狙いから外れた顔を外す

雰囲気が狙いと違う顔は外したくなりますが、**枚数を減らすと精度は必ず下がります**。
そこで「外したい顔」と「外してよい精度の下限」を `data/trim-candidates.json` に書いておき、
精度が足りてから外します。

```bash
npm run trim-check              # 判定するだけ
npm run trim-check -- --apply   # 条件を満たしていれば実際に削除する
```

いまの精度としきい値、外す候補、外したあとの見込みを表示します。
しきい値に届いていないとき、および外すと下回るときは削除しません。

### 髪と背景を色味で分ける

髪の長さは「髪色に近く、背景でも肌でもない画素」を数えて測ります。この判定には
**RGB の距離**と**色味（明るさを割り算で落としたもの）の距離**の2通りがあり、
片方で分けられなければもう片方を使います。

| | 分けられるもの | 分けられないもの |
|---|---|---|
| RGB の距離 | 黒髪 × 明るい背景（明るさの差が大きい） | 背景にグラデーションがあると埋もれる |
| 色味の距離 | 茶髪 × 灰色背景（R>G>B 対 R≒G≒B） | 黒髪（色味が灰色に近い） |

生成画像の背景は上から下へ暗くなっていることが多く、このムラは RGB をほぼ一様に
上下させます。色味を見ればそれが消えます。実例として、髪 (168,138,120) と
背景 (178,182,186) は **RGB 距離 80 に対し背景のムラ 79** で計測できませんでしたが、
**色味の距離 0.069 に対しムラ 0.005** と14倍の差があり、計測できます。

色味だけでは黒髪と灰色背景を分けられないので、**RGB で無地と言えるときは
これまで通り RGB で判定します**。既存96枚を新旧のコードで測り直し、
1440項目すべて値が変わらないことを確認しています。

### 測定ノイズを下げる

見分けられる段階数は「顔ごとの実測の幅 ÷ 測定ノイズ」で決まります。
ランドマークは解像度をわずかに変えるだけで少し動くため、1枚だけで測ると
その揺れがそのままノイズになります。

取り込み時に 896 / 944 / 992 / 1024px の4通りで測り、項目ごとに中央値を採ります。
揺れが打ち消し合ってノイズがおよそ半分になり、段階数は倍になります。

| | 1回だけ測る | 4通りの中央値 |
|---|---|---|
| 目の大きさ | 10段階 | **23段階** |
| あごのライン | 11段階 | **25段階** |
| 口の大きさ | 11段階 | **24段階** |

切り出し（表示用の画像）は 1024px のまま変わりません。

- 出やすさ … 結果に出る割合。21%（= 3/14）が公平
- 当てやすさ … 本当に重視している人のうち、ちゃんと出せた割合（再現率）
- 確からしさ … 出したうち、本当に重視していた割合（適合率）

プールを変えた前後で同じ400人と比べられます。

**顔を足しても、幅は縮んでいません。** 271枚 → 278枚 → 291枚と足してきましたが、
出やすさの幅は 1.52倍 → 1.40倍 → 1.40倍。偏る項目の顔ぶれが入れ替わるだけです
（278枚では輪郭の縦横比が x1.25 で最上位、291枚では眉と目の距離が x1.23）。

状態だったのは、髪の明るさ・長さ・肌の明るさが絶対値で大きく動くためでした。

**段階数と当てやすさは一致しません。** 髪の明るさは153段階で当てやすさ 75.7%、
眉の角度は50段階あって 56.0%、口の大きさは94段階あって 55.3% です。
逆に目の間隔は28段階しかないのに 65.9% です。
幅を広げれば当てられる、という話ではなく、他の項目と一緒に動く項目は切り分けられません
（鼻と口は互いに 0.80、目尻と眉の角度も 0.80）。**顔を足して幅を広げるときは、
段階数だけでなくこの表も見てください。**

**確からしさがいちばん低いのは小鼻の広さ 46.7%** です。上位3つに出しても、
半分以上は本当は重視していない人です。小鼻の広さは87段階あるのに口の大きさと
0.80 で動くため、「鼻を見ていた」と出しても実際は口だった、が起きます。

### 出やすさの水準をそろえる

出やすさの偏りには、相関とは別にもうひとつ原因があります。**重視度そのものの
水準が項目ごとに違う**ことです。重視度は `exp(a) * max(m, 1-m)^2` で決まるので、
理想値 m が端に寄りやすい項目は後ろの項が最大4倍になり、**重視していなくても
上位3つに紛れ込みます**。逆に中央へ寄る項目は、重視していても埋もれます。

実測では、出やすさの偏り（x1.45〜x0.76）と相関の関係は **-0.33** しかなく、
「重視していない人での重視度」との関係が **+0.55** でした。相関だけでは説明できません。

```bash
node tools/calibrate.mjs 45 400    # 水準をそろえる係数を求める
```

求めた係数は `src/calibration.js` に置き、重視度に掛けてから並べます。

**公平な割合ぴったりに強制してはいけません。** 係数を強くかけるほど出やすさはそろいますが、
その項目を本当に重視している人まで弾きます。115枚のときの実測では、輪郭の縦横比を
強制すると当てやすさが 63.0% → 47.1% まで落ちました。

305枚での実測（係数を求めたのとは**別の乱数**で測り直した値。
同じ乱数で測ると過学習するので当てになりません — CLAUDE.md 参照）

| 強さ | 出やすさの幅 | 当てやすさの幅 | いちばん当てにくい項目 |
|---|---|---|---|
| 0.00（かけない） | 1.91倍 | 1.74倍 | 44.4% |
| **0.45** | **1.43倍** | **1.37倍** | **55.1%** |
| 0.80 | 1.41倍 | 1.40倍 | 54.6% |
| 1.00（公平な割合に強制） | 1.48倍 | 1.53倍 | 51.0% |

**0.45 で3つとも同時に良くなります。** 強くかければそろうというものではなく、
305枚では 1.00（公平な割合に強制）が出やすさの幅でも 0.45 に負けています。
較正しても診断の精度自体は変わりません（`npm run acc-check` が4つとも ±0.3ポイント以内）。

**残る 1.43倍 / 1.37倍 は係数では詰められません。** 当てやすさは項目どうしの
相関で決まっており（115枚のときの実測で相関 -0.70）、動かすには顔を足すしかありません。

### 項目ごとの偏りを直す

出やすさが項目ごとに偏る原因は**項目どうしの相関**です。ランク正規化で各項目の
分布は同じ一様分布にそろうので、残る違いは相関しかありません。実測でも
**「その項目の最大相関」と「当てやすさ」の相関は -0.78** でした。

115枚のときの実測です。

| 項目 | 当てやすさ | いちばん強い相関 |
|---|---|---|
| 唇の厚さ | 80.6% | 0.55（髪の明るさ） |
| 目の大きさ | 74.1% | 0.58（輪郭の縦横比） |
| 眉と目の距離 | 58.0% | **0.83（眉の形）** |
| 眉の形 | 57.3% | **0.83（眉と目の距離）** |
| 眉の角度 | 51.4% | **0.76（目尻の角度）** |

彫りが深い顔はだいたい平行眉、眉と目が離れた顔はだいたいアーチ眉 ——
このように2項目がいつも一緒に動いていると、**どちらを重視しているのか切り分けられません**。

いまの291枚での最大相関は次のとおりです（`npm run coverage -- data/faces.json`）。
**眉まわりは狙いどおり下がり、いちばん重いのは鼻と口に移りました。**
なお下の表はプール全体の値で、`cute` 層だけで測ると 小鼻の広さ ↔ 口の大きさ が
0.81、目尻の角度 ↔ 眉の角度 が 0.80 です。

```bash
node tools/balance.mjs --size 52 --cand 候補.json   # 相関が小さくなる組み合わせを探す
```

**ただし選び直しでは公平になりません。** 手持ち71枚から52枚を選び直すと
最大相関は 0.83 → 0.71 まで下がりますが、偏りの幅は 1.9倍 → 1.8倍 とほぼ変わらず、
弱い項目が良くなる代わりに別の項目が悪くなります（眉の角度 51→63%、口の大きさ 57→69%、
一方で小鼻 71→60%、目尻 64→58%）。枚数を 36枚まで減らしても最大相関は 0.65 止まりです。

**公平にするには、相関を切る顔を新しく作るしかありません。**

```bash
node tools/generate.mjs --decorrelate --count 24 --dry-run   # 作るべき顔のプロンプト
node tools/gap-check.mjs 候補.json                            # その顔が枠を埋めるか
```

強く相関している2項目を中央値で4分割し、**空いている組み合わせだけ**を名指しで
作らせるプロンプトを出します。指定は必ず2項目だけです（3つ以上重ねると顔が崩れるため）。
`tools/balance.mjs` は足りない組み合わせを枚数つきで表示します。
`tools/gap-check.mjs` は、手元の候補がその枠を埋めるかどうかを1枚ずつ判定します。

**必要な枚数の目安**（いちばん重い「眉と目の距離 ↔ 眉の形」を、空いている2象限に
半々で足したときの見込み）

| 足す枚数 | +4 | +8 | +16 | +24 | +32 |
|---|---|---|---|---|---|
| r | 0.77 | 0.68 | 0.54 | 0.42 | 0.32 |

数枚では動きません。**1組あたり16枚以上**が目安です。
ただし1枚が複数の枠を同時に埋めることはあります（`gap-check` が何件埋めるか出します）。

**実際に60枚作ったときの結果**（59枚 → 115枚。重複候補4枚を除いて56枚を取り込み）

12枠へ5枚ずつを狙って60枚生成したところ、`gap-check` の判定は
**枠を埋めたのが38枚 / 埋めなかったのが22枚**、延べ64件で **12枠中11枠**が埋まりました。

| 結果 | 取り込み前 59枚 | 取り込み後 115枚 |
|---|---|---|
| 最大相関 | 0.86（眉と目の距離 ⇔ 眉の形） | **0.77**（小鼻の広さ ⇔ 口の大きさ） |
| 眉と目の距離 ⇔ 眉の形 | 0.86 | **0.75** |
| 重要特徴 Top3 的中（30問・adaptive） | 55.0% | **58.9%** |

**狙った枠に均等には入りません。** いちばん入ったのは「シュッとした鼻×大きめの口」と
「ツリ目×下がり眉」で各12枚、いちばん少ない「眉と目が離れている×平行眉」は1枚、
「タレ目×上がり眉」は**5枚指定して0枚**でした。生成器は指示どおりの組み合わせを
作れないことがあるため、**枚数は多めに見積もり、`gap-check` で入った数を確かめてください**。

#### 1組に集中させても眉は動かなかった

枚数が少ないときに12枠へばらまくと1枠1〜2枚にしかならないので、`--pair` で
1組だけに集中させられるようにしました。

```bash
node tools/generate.mjs --decorrelate --pair browAngle,browArch --count 16
```

当てやすさがいちばん低い「眉の角度」を狙い、`眉の角度 ⇔ 眉の形`（r=-0.76）の
空いている2象限へ8枚ずつ、計16枚を作りました。**結果は失敗です。**

| | 指定 | 実際に入った |
|---|---|---|
| 下がり眉 × 平行眉 | 8枚 | **1枚** |
| 上がり眉 × アーチ眉 | 8枚 | **1枚** |

16枚中2枚しか狙った枠に入らず、相関は 0.761 → 0.760 とほぼ動きませんでした。
足すとむしろ全体が悪くなります（45問・400人）。

| | 115枚 | +16枚 = 131枚 |
|---|---|---|
| 出やすさの幅 | 1.51倍 | 1.67倍 |
| 当てやすさの幅 | 1.43倍 | 1.63倍 |
| いちばん当てにくい項目 | 58.3% | 51.2% |
| 最大相関 | 0.790 | 0.797 |

そのため、この16枚は取り込んでいません。

**眉の角度と眉の形は、プロンプトで描き分けられません。** 輪郭や鼻の組み合わせは
ある程度入るので（60枚のときは12枠中11枠が埋まった）、これは枚数ではなく
眉という部位の問題です。

#### 邪魔をしていたのは、かわいさの押さえ

`--decorrelate` のプロンプトは末尾に
`still a strikingly pretty and cute face` を必ず足していました。
これがあると生成器は「かわいい顔の正解値」から離れられず、
**その正解値から遠い側の象限が作れません**。

24枚（かわいさ付き）での実測では、対になる2象限のうち片側しか埋まりませんでした。

| 枠 | 入った数 |
|---|---|
| シュッとした鼻 × 大きめの口 | 5 |
| 小鼻がしっかりした鼻 × 小さめの口 | **0** |
| タレ目 × 上がり眉 | 4 |
| ツリ目 × 下がり眉 | 2 |

**片側だけ厚くすると相関はむしろ強まります。** この24枚を足すと、
予測一致率 0.850 → 0.835、較正前の出やすさの幅 1.90倍 → 2.67倍 と
すべて悪化しました（足していません）。

`--vibe neutral` を渡すと、この押さえの一文ごと外して実測値の側を優先します。

```bash
node tools/generate.mjs --decorrelate --vibe neutral --count 24
npm run analyze -- --from <画像フォルダ> --tier plain --append
```

かわいさを外した顔は **`--tier plain` で取り込みます**。
`plain` 層は同じ層どうしでしか並ばず（「仕組み 5」）、その回は
スキップも閉じます。見たい顔ではないぶん飛ばされやすいのに、
顔のパーツの幅がいちばん広いのがこの層だからです。

`--soft` を渡すと、前置きのかわいさは残して末尾の念押しだけを外せます。
`--fill` だけでなく `--decorrelate` でも効きます（以前は無視されていました）。
端の顔（`tier: edge`）はこの設定で作れています。

#### 既定モデルでは、枠に入らず重複が出る

`--soft` を効かせたうえで、いちばん重い `小鼻の広さ ⇔ 口の大きさ`（`cute` 層 0.81）
の空いている2象限だけを狙い、16枚を試しました（`--vibe idol --soft` と
`--vibe student --soft` を8枚ずつ）。

| | idol + soft | student + soft |
|---|---|---|
| 狙った2象限に入った | 2/8 | 2/8 |
| 8枚足したときの最大相関 | 0.938 → 0.937 | 0.938 → **0.942** |

**命中率は25%です。** 16枚の内訳はこうなりました。

| | 枚数 | |
|---|---|---|
| 既存プールと重複（見た目 0.20 以下） | 3 | 生成器が**プールにすでにある顔を作り直している** |
| 短髪（かわいさの基準に届かない） | 6 | 本人の判断。`cute` 層に入れられない |
| **取り込んだ** | **7** | かわいさ合格・重複なし |

取り込んだ7枚の効果は、ほぼありません。

| | 271枚 | +7枚 = 278枚 |
|---|---|---|
| `cute` 層の最大相関 | 0.805 | 0.811 |
| 予測一致率（30問・200人・adaptive） | 0.815 | 0.820 |
| 重要特徴 Top3 的中 | 54.7% | 54.5% |
| `cute` 層の段階数合計 | 478 | 486 |
| 眉と目が離れている側の枚数 | 7枚 | 7枚 |

精度は下がらないので取り込みましたが、**相関はわずかに悪化しています**。
`npm run pick` の判定は 0枚（段階数の合計 465 → 465）でした。

ここで分かったのは、**この撮り方・この水準で、既定モデルが作れる顔は
ほぼ出尽くしている**ということです。新規16枚のうち3枚が既存プールとの重複で、
うち1枚は `plain` 層の顔の作り直しでした。
この読みは当たっていて、**モデルを変えると重複が消えます**（下記）。

> **短髪は `cute` 層に入れません。** かわいさの基準は人が決めるという決まりのとおり、
> 16枚を本人に見せて決めた基準です。髪の長さの実測値で機械的に切ると
> ボブまで落ちてしまうので（0.58 や 0.26 でもボブでした）、目で見て判断します。

#### 生成器は出尽くす。逃げ道はモデルを変えること

既定の `gemini-3.1-flash-image` は、**プールにすでにある顔を作り直します**。
別のモデルに変えると重複が消えます。同じプロンプト・同じ設定で比べた実測です。

| モデル | 枚数 | 既存プールとの重複（見た目 0.20 以下） | プールとの平均距離 |
|---|---|---|---|
| `gemini-3.1-flash-image`（既定） | 36 | **8枚（22%）** | 0.21 |
| `gemini-2.5-flash-image` | 28 | **0枚** | **0.27** |

狙った枠への命中率も上でした。いちばん重い `小鼻の広さ ⇔ 口の大きさ` の
空き2象限を狙うと、別モデルは **10枚中6枚**が入り、既定モデルの
`--fill` は 20枚中5枚でした。README が長く「作れない」と書いてきた
`タレ目 × 上がり眉` にも入っています。

```bash
npm run generate -- --decorrelate --pair noseWidth,mouthWidth \
  --model gemini-2.5-flash-image --vibe idol --soft --count 10
```

**顔の系統は変わります。** 別モデルはアイドル系というより大人っぽい寄りで、
短髪も出やすくなります。かわいさの採否は必ず人に見てもらってください。

#### 眉は、モデルを変えても動かない

`--pair eyeTilt,browAngle`（`目尻の角度 ⇔ 眉の角度`、r=0.80）を別モデルで
10枚狙いましたが、枠に入ったのは **3枚**で、6枚はどの枠も埋めませんでした。
同じモデルで鼻×口を狙った10枚が6枚入ったのと比べると、明確に低いです。

**眉を名指しで狙うのは、モデルを変えても無駄です。** ただし鼻×口を狙った顔が
ついでに眉の枠に入ることはあるので、眉は「直接狙う」のではなく
「他を狙った結果として埋まる」ものとして扱ってください。

#### 短髪を大量に足すと、かえって偏る

重複を外した候補49枚を全部足すと、`目尻の角度 ⇔ 眉の角度` が
0.811 → **0.815** と悪化しました。髪の長さ 1.0 以上の13枚だけに絞ると
0.811 → **0.804** に下がります。短髪の多くは眉を狙った生成で出たもので、
既存の相関どおりの顔だったためです。

**枚数ではなく、どの顔を足すかで決まります。**

#### 出題の工夫では引き出せない

相関した2項目を切り分けるには「片方だけが違うペア」を見せればよいはずです。
そこで、プール内の相関どおりに動いているペアを避け、期待からのズレ
`|db - r*da|` が大きいペアを選ぶ項目を `choosePair` に足して試しました。
**強くするほど悪くなります。**

| 設定 | 出やすさの幅 | 当てやすさの幅 | いちばん当てにくい項目 | 平均 |
|---|---|---|---|---|
| いまのまま | 1.56倍 | 1.46倍 | 55.6% | 70.3% |
| ズレ重視 ×3 | 1.71倍 | 1.57倍 | 52.9% | 69.5% |
| ズレ重視 ×8 | 2.16倍 | 1.97倍 | 45.2% | 64.2% |

**プールに無い組み合わせは、出し方を変えても出てきません。** 相関を外れたペアを
無理に探すと、情報量の多い普通のペアを捨てることになり、全体が崩れます。
切り分けたいなら、その組み合わせの顔をプールに入れるしかありません。

#### 残差は足りている

「相関を除いた幅が測定ノイズに埋もれているのでは」とも考えましたが、違いました。

| 項目 | 全体の段階数 | 最大相関 | 相関を除いた段階数 | 当てやすさ |
|---|---|---|---|---|
| 目の間隔 | 28 | 0.53 | 24 | **76.6%** |
| 眉の角度 | 48 | 0.77 | 31 | **58.3%** |
| 輪郭の縦横比 | 58 | 0.66 | 43 | 58.7% |

眉の角度は目の間隔より残差が広いのに、当てやすさは低いままです。
当てやすさとの相関は、相関を除いた段階数が **0.53**、最大相関が **-0.68** で、
効いているのは**相関そのもの**です。測り直しても精度は上がりません。

### 顔プールが診断に使えるか確かめる

実測値の幅が狭いとき、それが「顔が本当に似ている」のか「測定ノイズに埋もれている」のかは、
数値を眺めるだけでは分かりません。同じ画像を少しずつ違う解像度で解析するとノイズが測れます。

```bash
npm run noise-check -- <画像フォルダ>
```

項目ごとに「顔ごとの差」と「測定ノイズ」を並べて表示します。
比が 3 倍以上あればその項目は診断に使えます。1.5 倍を下回る項目は、
顔の差がノイズに埋もれているので結果を信用できません。

### API で顔をまとめて生成する場合

キーの渡し方は2通りあります。どちらでも `tools/generate.mjs` はそのまま動きます。

| | 設定場所 | キーの見え方 |
|---|---|---|
| 環境変数 | クラウド環境の **Environment variables** に `GEMINI_API_KEY=...` | セッション内から読める |
| API credential | クラウド環境の **API credentials**（Pro / Max のみ） | セッションには届かない。プロキシが付ける |

後者のほうが安全です。登録はこうします。

- **Allowed websites**: `generativelanguage.googleapis.com`
- **Custom headers**: 名前 `x-goog-api-key` / Prefix は空 / 値にキー

どちらも、設定できる場所は claude.ai/code の**メッセージ欄の上にある雲のアイコン**（いまの環境名が出ているボタン）です。設定ページや直リンクはありません。環境の行の歯車を開くと、Environment variables と API credentials が並んでいます。
**変更は次に始めるセッションから効きます**（実行中のセッションは起動時の値を持ち続けます）。


```bash
GEMINI_API_KEY=xxxx npm run generate -- --count 160 --out .cache/raw
npm run analyze -- --from .cache/raw
```

> **`--image-size` は既定モデルでは効きません。**
> `gemini-3.1-flash-image` はこの指定を受け付けず、
> `imageSize=0.5K は ... 使えないため、指定なしで続行します` と出て **1024×1024（1K）** で生成されます。
> 安くするつもりで `0.5K` を付けても単価は下がりません。

使う額に上限をつけるときは `--budget-jpy` を付けます。予算を枚数に直してから
プロンプトを切り詰めるので、**実行中に上限を超えることはありません**。

```bash
npm run generate -- --decorrelate --count 60 --budget-jpy 500 --out .cache/decor
# → 予算 500円 / 1枚あたり約7.2円 → 最大 69枚。60件は予算内です（見込み 約432円）
```

**実測の単価**（`gemini-3.1-flash-image` / 1024×1024 / 2026年9月）

**1枚あたり約12.5円（≒ $0.078）** です。254枚の生成でプリペイド残高が
**3,170円** 減った実測値（2,522円 → -648円）。

| 枚数 | 概算 |
|---|---|
| 24枚 | 約300円 |
| 60枚 | 約750円 |
| 160枚（`--count` の既定値） | **約2,000円** |

`--count` の既定値は160枚です。**そのまま実行すると二千円を超えます。**
`--budget-jpy` で上限を決めて回してください。

> **請求は遅れて反映されます。** 10枚作った直後に残高を見ても変わっていない
> ことがあり、後からまとめて引かれます。「減っていないから大丈夫」と判断せず、
> `--budget-jpy` の上限だけを頼りにしてください。

> **以前ここには 1枚7.4円 と書いてありました。これは誤りでした。**
> 60枚で444円という初回の実測から出した値でしたが、請求の遅れで
> 一部しか反映されていない時点の差分を見ていたためです。
> `--usd-per-image` の既定値もその誤った値（$0.045）だったため、
> `--budget-jpy` が予算の1.7倍の枚数を通してしまい、
> 2,000円の予定で3,170円を使う事故を起こしました。

> **クレジット残高とは別に、プロジェクトの月額上限があります。**
> 上限に達すると `429 RESOURCE_EXHAUSTED / exceeded its monthly spending cap` が返ります。
> 残高が残っていても生成できません。https://ai.studio/spend で引き上げてください。
> 予算を決めているなら、ここを予算額に設定しておくと安全弁になります。
>
> この 429 は待っても解消しないので、`generate.mjs` は再試行せずに理由を出して止まります
> （以前はレート制限として扱い、20秒ごとに再試行し続けて無言で止まって見えていました）。

> **Gemini の画像生成には課金の有効化が必要です。**
> 画像生成モデルには無料枠が存在せず（料金表の無料枠欄が「利用不可」）、
> 無料枠のプロジェクトからは `limit: 0` のエラーになって1枚も生成できません。
> AI Studio の画面上での生成は無料ですが、API経由とは別枠です。

| オプション | 既定値 | 説明 |
|---|---|---|
| `--count` | 160 | 生成枚数 |
| `--model` | `gemini-3.1-flash-image` | `--list-models` で利用可能なモデルを確認できます |
| `--image-size` | `0.5K` | 出力解像度。単価に直結します（0.5K なら1枚 $0.045 程度）。**`gemini-3.1-flash-image` では無効**（上記） |
| `--budget-jpy` | – | 使う上限（円）。枚数に直して切り詰めるので、実行中に超えません |
| `--usd-per-image` | `0.045` | 1枚あたりの単価。予算計算に使う（実測は約 $0.047） |
| `--jpy-per-usd` | `160` | 為替。多めに見積もるほど枚数が減り、超えにくくなる |
| `--ethnicity` | `japanese` | `japanese` / `eastasian` / `mixed` / `global` |
| `--vibe` | `idol` | `idol`（アイドル・女優くらいのかわいさ／化粧あり）/ `student`（かわいい女子大学生）/ `cute`（かわいい雰囲気）/ `neutral`（指定なし）。`--decorrelate` では `neutral` にすると、かわいさの押さえを外して狙った象限を作れるようにする |

年齢は18〜25歳を割り当てます。大学生にあたる18〜22歳を厚めにしています。
顔を好みで採点するアプリのため、未成年にあたる年齢は生成しません。
年齢を1点に揃えないのは、揃えると「顔立ちの印象（童顔↔大人顔）」の軸が
測れなくなるためです。
| `--female-ratio` | 0.5 | 女性の割合 |
| `--pair` | – | `--decorrelate` で1組だけに集中させる（例 `browAngle,browArch`）。枚数が少ないときに使う |
| `--dry-run` | – | 課金せずプロンプトだけ書き出す |

`japanese` と `eastasian` では、肌と髪の選択肢が現実的な範囲に差し替わります
（「deep brown skin の日本人」のような矛盾した指定を避けるため）。

## 検証

顔プールを使った通しの動作確認として、特定の特徴だけを基準に選び続ける仮想ユーザーを
ブラウザ上で自動操作させ、その特徴を診断が言い当てられるかを確認しています。

| 選び方 | 診断結果 | 重視度 | 一貫性 |
|---|---|---|---|
| 目が大きいほう | ぱっちり目 | 92% | 94% |
| ツリ目なほう | ツリ目 | 93% | 94% |
| 唇が厚いほう | ぽってり唇 | 95% | 94% |

「髪が長いほう」で選び続ける仮想ユーザーも確認していましたが、髪の長さは
診断項目から外したので（[髪の長さは測っても診断には使わない](#4-髪の長さは測っても診断には使わない)）
いまは対象外です。

`npm run noise-check` では、実測する15項目すべてで顔ごとの差が
測定ノイズの 4〜111 倍あることを確認しています（115枚時点）。

### スキップについて

「どちらもピンとこない」を押した回は記録せず、**回数にも数えません**。
シミュレーションでは、迷う組だけをスキップしても精度はほぼ変わらず
（30回で84.3% → 84.0〜85.1%）、迷う組の回答はもともとコイン投げに近く
情報がほとんど無いことが確認できました。

一方、内容に関係なくスキップすると回答数がそのまま減り、精度は落ちます
（50%スキップで76.9%）。そのためスキップは回数を消費しない扱いにして、
画面に出している精度（答えた回数に対する値）と実態がずれないようにしています。

スキップを閉じる（画面に **NO SKIP** と出る）のは次の2つです。

- 判定が動く組み合わせ（`pairValue` が 0.38 以上）。45問のうち2割ほど
- **`plain` 層どうしの回。必ず閉じます**

後者は「仕組み 5」の通りで、見たい顔ではないぶん飛ばされやすいのに、
顔のパーツの幅がいちばん広いのがこの層だからです。
